"GET" OCR API Endpoint
Using an OCR API was never easier...
Besides the full-featured "POST" OCR API at /parse/image we provide an additional OCR API endpoint
at /parse/ImageUrl for GET requests. While not as versatile as the POST API,
it is very easy to use. Everything you need for the api call is inside the URL.
Example (just click the link to start the OCR):
https://api.ocr.space/parse/imageurl?apikey=helloworld&url=https://dl.a9t9.com/ocr/solarcell.jpg
The default OCR language is English for OCR Engine1, or "Auto" for OCR Engines 2 and 3.
https://api.ocr.space/parse/imageurl?apikey=helloworld&url=https://dl.a9t9.com/ocr/solarcell.jpg&language=chs&isOverlayRequired=true
The important limitation of the GET api endpoint is it only allows image and PDF submissions via the URL method, as only
HTTP POST requests can supply additional data to the server in the message body. GET requests include all
required data in the URL. So by design, a GET api cannot support file uploads (file parameter)
or BASE64 strings (base64image). Also, note the url
for calls by weblink (GET) is .../IMAGEURL not .../IMAGE as for the regular OCR API.
The GET API is easy and fast to use. Just note that the URL with the api key might be stored in your browser's history. But this is not a security problem because even if somebody gains access to your personal API key,
he or she can not access any information about you or the OCR'ed documents, because we do not store such information in the first place.
The worst-case scenario is that somebody uses all your free conversions. If this might be a problem for your
application, simply continue to use the fully SSL-encrypted POST version of the API or switch to the PRO OCR API, which provides additional options.

Language used for OCR. For Engine 2 and 3 the default is auto (automatic language detection), so you can simply omit the parameter. For the deprecated Engine 1, the default is English eng.

isOverlayRequired
[Optional] Boolean value
Default = False
If true, returns the coordinates of the bounding boxes for each word. If false, the OCR'ed text is returned only as a text block (this makes the JSON reponse smaller).
Overlay data can be used, for example, to show text over the image.
For Japanese, Chinese and Korean text, Engine 1 and 2 return one Words entry per character, with the bounding box fitted to the character. Digits and Latin words remain word-level. The text output is the same either way.
filetype
[Optional] String value: PDF, GIF, PNG, JPG, TIF, BMP
Overwrites the automatic file type detection based on content-type. Supported image file formats are
png, jpg (jpeg), gif, tif (tiff) and bmp. For document ocr, the api supports the Adobe PDF format. Multi-page TIFF files are supported.
detectOrientation
[Optional] true/false
If set to true, the api autorotates the image correctly and sets the
TextOrientation
parameter
in the JSON response. If the image is not rotated, then TextOrientation=0, otherwise it is the degree of the rotation, e. g. "270".
isCreateSearchablePdf
[Optional] Boolean value
Default = False
If true, API generates a searchable PDF. This parameter automatically sets isOverlayRequired = true.
isSearchablePdfHideTextLayer
[Optional] Boolean value
Default = False. If true, the text layer is hidden (not visible)
scale
[Optional] true/false
If set to true, the api does some internal upscaling. This can improve the OCR result significantly, especially for
low-resolution PDF scans. Note that the front page demo uses scale=true, but the API uses scale=false by default. See also this
OCR forum post.
isTable
[Optional] true/false
If set to true, the OCR logic makes sure that the parsed text result is always returned line by line. This switch is recommended for
table OCR, receipt OCR, invoice processing and all other type of
input documents that have a table like structure.
OCREngine
[Optional] 1 or 2 or 3
Engine 2 is default and used if no OCR engine is selected. See OCR Engines.
Tip: When serving images from an Amazon AWS S3 bucket, Google cloud storage or a similar services for use with the "URL" parameter, make sure the file link has the right content type.
It should not
be "Content-Type:application/x-www-form-urlencoded" (which seems to be the default for AWS) but image/png or similar for images. For PDF documents make sure the content type is
not "image/pdf" but application/pdf. You can check the content type of your links with various free
"MIME content type checker" websites. The OCR API uses the content type to automatically detect the correct file type.
But if you have the wrong content-type and can not change it (e.g. because you do not control the cloud storage), no problem:
In this case you can overwrite the automatic file type detection by adding the
the filetype= parameter and tell the API directly what type of document you are sending (PNG, JPG, GIF, PDF).

Select the best OCR Engine
The OCR API offers multiple OCR engines, each with its own processing logic. We recommend trying all of them
and using whichever produces the best result for your input. You can compare engines directly on our
online OCR portal on the front page, or switch between them in your API calls using the
OCREngine=1/2/3 parameter.
Features of OCR Engine 1
Engine 1 is our original OCR engine. It has served us well and is now retired, because Engine 2 and 3 are better in every way.
Please use Engine 2 or Engine 3 instead. Calls to Engine 1 are automatically redirected to Engine 2.
Supports many languages, including Asian languages such as Chinese, Japanese, and Korean
Supports multi-page TIFF scans
Parameter: OCREngine=1
Features of OCR Engine 2
Engine 2 is the default engine and often the best all-round choice, offering the strongest balance of speed and quality.
It is used automatically if no OCR engine is selected. If you're not sure which engine to use, start here.
Language auto-detection is the default (language=auto, or simply omit the parameter). It handles documents that mix
languages or scripts and reads vertical Japanese and Chinese text. The specific
language codes are deprecated; if an existing integration still sends one, it is used only as fallback when auto-detection fails.
Supports 33 languages:
Latin script: English, French, Italian, German, Spanish, Portuguese, Turkish, Indonesian, Malay, Czech, Danish, Dutch, Norwegian (Bokmål and Nynorsk), Polish, Romanian, Swedish, Finnish, Vietnamese (see Latin languages)
Cyrillic script: Russian, Ukrainian
CJK: Chinese (Simplified and Traditional), Cantonese (Simplified and Traditional), Japanese, Korean
Other scripts: Arabic (including Najdi Arabic), Thai, Hindi, Marathi
Languages without a dedicated model but written in Latin or Cyrillic script (for example Croatian, Slovak,
Slovenian, Hungarian, Bulgarian, Serbian) are read through the Latin and Cyrillic recognizers; expect
occasional diacritic errors there. Greek is not supported by Engine 2 yet.
With isOverlayRequired=true, Japanese, Chinese and Korean text
is returned with one bounding box per character, fitted to the character
Strong recognition also of special characters such as §$@€/()[]{}
Strong recognition of text on noisy or unusual backgrounds like photos, road signs,
license plates, memes, and even some CAPTCHAs
Often good for single-digit, single-character, and alphanumeric OCR; for example
Sudoku puzzles,
dot-matrix text,
MRZ passport zones,
single digits,
and cases where the
first letter is dropped.
But Engine3 (see below) is even better for single-digit and single-character OCR.
Works with rotated text (see forum:
detecting rotated text on image spam)
Parameter: OCREngine=2
Features of OCR Engine 3
Engine 3 is our newest engine and delivers the highest OCR accuracy, including for handwriting, tables, and 200+ languages. The trade-offs are slower processing on larger files and lower monthly conversion limits.
Supports more than 200 languages with auto-detection (no language code required)
Precise table recognition, with tables returned in
Markdown format
Strong handwriting recognition
Checkbox recognition: ☐, ☑
Slower than Engine 1/2 on larger images and PDFs. Processing time grows noticeably
with file size.
Searchable PDF output is supported with the same parameters as Engine 1/2
(isCreateSearchablePdf, isSearchablePdfHideTextLayer). The text layer is placed
per recognized text region rather than per word, so text selection in the PDF is a bit coarser than with Engine 2.
Engine 3 prioritizes OCR accuracy and Markdown output
over spatial precision. Overlay data (x/y bounding boxes per word) is available, but coordinates are
not as precise as Engine 1/2. Requesting overlay data (isOverlayRequired=true)
also makes the call 2-3× slower; on Engine 1/2 the same option has almost no performance cost.
Monthly conversion limits. Engine 3 is significantly more compute-intensive per
conversion, so it has its own quota:
Free plan: 1000 Engine 3 conversions in addition to the 25,000 for Engine 1/2
PRO / PRO PDF plan: 30,000 Engine 3 conversions in addition to the 300,000 for Engine 1/2
Parameter: OCREngine=3

Searchable PDF
You can create searchable PDFs (sometimes also called Sandwich PDFs) directly via the API. The PDF is returned as download link
in the API JSON response the form of "SearchablePDFURL": "...".
The download link is valid for one hour, after this time the document is deleted from our OCR servers.
The isCreateSearchablePdf = true switch triggers the generation of the searchable PDF. By default,
the added text layer is visible - - this is ideal for testing the result as you can compare the OCR'ed output directly with the scan image.
By adding isSearchablePdfHideTextLayer = true you make the text layer invisible.
Creating a searchable PDF from the OCR result takes additional processing time, so you should only activate this
feature if you need the OCR result in PDF format.
NOTE: You must use both parameters, isCreateSearchablePdf = true and
isSearchablePdfHideTextLayer = false or true, otherwise the generated PDF contains no text layer.
When used with the free OCR API tier, the generated PDF contains a
watermark "Generated by OCR.space" in the lower right corner.
With the PRO OCR API, no watermark is added to the PDF.

cURL command-line
(a) Provide image/PDF to be OCR'ed via URL
curl https://api.ocr.space/Parse/Image -H "apikey:helloworld" --data "isOverlayRequired=true&url=http://dl.a9t9.com/blog/ocr-online/screenshot.jpg&language=eng"
curl is an open source command line tool and library for transferring data with URL syntax.
The libcurl library is portable. It builds and works identically on nearly any platform (Windows, Mac, Linux,...).
(b) Upload image/PDF to be OCR'ed from your server/PC
curl -H "apikey:helloworld" --form "[email protected]" --form "language=eng" --form "isOverlayRequired=true" https://api.ocr.space/Parse/Image
Note: @screenshot.jpg assumes an image with name "screenshot.jpg" is in the same directory as cURL.exe. Note that the isOverlayrequired (default: no) and the language (default: eng) parameters are optional.
(c) Send image as string in Base64 format
curl -H "apikey:helloworld" --form "base64Image=data:image/jpeg;base64,/9j/AAQSk [Long string here ]" --form "language=eng" --form "isOverlayRequired=false" https://api.ocr.space/parse/image
The base64 string in this example is truncated.
